# GNU RISC-V Upstream 情报收集

## 背景
在 ruyisdk 包管理器中，gnu Toolchain 的 打包和分发二进制，免去用户通过源码编译构建的过程，是包管理器的核心价值之一。

近期有合作伙伴（进迭时空）提出：他们已经在上游合入了对 K3 芯片的支持性 patch ，建议我们可以更新下 gnu-upstream 版本，提供最新的支持了 K3 的gnu新版本。

基于上面的需求，我们意识到 ruyi 需要对 基础组件的上游进行信息获取和分析，根据一些重要的特性（比如 对芯片的支持、新扩展指令的支持、profile 规范支持等等，尤其适合进行打包新版本的重要特性）保持高度的关注，方便我们在合作的过程中占据主动性，可以及时的跟进这些特性及时发布新版本。


## 需求

GNU上游仓库（主要是针对riscv架构的官方上游）
针对这个仓库的动态进行监控，实现动态监控，能够自动识别重要的进展和更新，包括但是不限于对芯片的支持、重要的扩展和profile等支持（比如 进迭时空K3 的支持已经合入到仓库这种对开发板支持的工作等。）
——》主要是从gnu用户的角度，适合构建出新二进制的重要更新，ruyi包管理器计划根据这个更新来进行打包和gnu二进制分发。

技术要求：
- 最好是脱离本地环境，利用 github action 定时任务完成周期性监控
- 监控频率：一周一次(或者一个月一次）
- 后续计划与飞书企业群对接，消息自动发送到飞书群中

## 输出要求
- fork仓库 https://github.com/xijing21/ry-wf-auto  ，在仓库的 upstream-tracker 下贡献相关代码，具体参考 https://github.com/xijing21/ry-wf-auto/blob/main/upstream-tracker/readme.md  （可调整，但是需要遵守任务相关的文件都在upstream-tracker 下）

以下是豆包的思路和方案（仅供参考）：

# 整体技术思路（无本地环境依赖，周期性情报采集，面向Ruyi包管理器打包决策）
核心定位：**GNU RISC-V上游仓库情报采集系统，不是本地编译/构建系统；只做代码变更元信息抓取+语义识别，输出情报摘要，辅助判断是否需要触发Ruyi打包新GNU二进制**
> 采集对象：binutils、gcc、glibc、gdb（GNU四大核心，RISC-V架构主线上游），重点关注RISC-V相关PR/Commit，例如：进迭K3开发板支持、RISC-V ISA扩展、profile、硬件平台port、ABI变更等。

## 一、架构选型（满足：不依赖你的本地电脑，周期拉取，只拿commit/pr元数据）
方案：**基于GitHub/GitLab REST API + 定时云函数（Serverless）**
- 运行载体：GitHub Actions（推荐GitHub Actions，免费，开箱即用
- 触发方式：定时 cron（每周1次 / 每月1次，可配置）
- 采集内容：**只拉元数据（commit message、PR标题、PR描述、文件变更路径），不拉完整源码，不做本地编译**
> 优点：不需要在你电脑部署任何环境；所有抓取、解析、识别全部在云端一次性跑完；每次执行完销毁运行环境，无常驻服务。

### 数据源说明
GNU项目大部分托管在 `sourceware.org` 的git仓库，同时有GitHub镜像：
1. 官方主仓库：git://sourceware.org/binutils-gdb.git，git://sourceware.org/git/glibc.git，git://gcc.gnu.org/git/gcc.git
2. 镜像仓库（优先用镜像API，访问稳定）：github.com/bminor/binutils-gdb、github.com/bminor/glibc、mirrors/gcc

> API选择：优先GitHub REST API，可直接查询：
> - 指定分支（`master` / `main`）最近一段时间新增commit
> - 新增PR（pull request）、PR合并记录
> - 过滤文件路径（只关注 `riscv-*` 相关目录，过滤掉x86/arm等无关代码）

## 二、处理流水线（4步，每次定时任务自动执行）
### Step1：增量拉取（只抓窗口内新增变更，避免重复）
配置时间窗口：比如最近7天（每周跑）/最近30天（每月跑）
过滤规则：
1. 仓库白名单：gcc、binutils-gdb、glibc、gdb
2. 分支白名单：上游主线开发分支（稳定分支可选单独监控）
3. 路径过滤：只匹配目录含 `riscv` 的变更，跳过其他架构代码
> 输出原始数据：commit hash、提交人、commit message、PR编号、PR标题、PR body、修改文件列表

> 关键点：**只拉文本元信息，不clone完整仓库，流量和耗时极低**

### Step2：语义识别（核心，区分「普通bug修复」vs「值得打包的重要更新」）
做关键词+规则匹配（轻量文本匹配，不需要大模型也可以；可选接入LLM做更精准的摘要分类）
#### ✅ 判定为【高价值，需要通知Ruyi打包评估】的特征
1. RISC-V硬件平台/开发板支持：`k3`、`jiandie`、board、machine、soc，新增硬件target（比如进迭K3平台port）
2. RISC-V ISA扩展：`Zce`、`Zfh`、`Zvl`、`Zk` 等各类扩展指令集支持
3. Profile / ABI变更：`RISC-V profile`、`rv64gc`、ABI、ILP32、LP64，规范相关改动
4. 重要架构特性：vector、crypto、hypervisor等大模块支持合入主线
5. Target/配置选项新增：新增`-march`、`-mabi`编译选项

#### ⚠️ 判定为【低价值，仅记录，不触发打包评估】
- 普通warning修复、代码清理、注释修改、测试用例微调
- 只针对其他架构的提交
- 临时PR未合入（只监控**已经合并进上游主线**的PR/commit，不看草稿PR）——> 如果是上面“✅ 判定为【高价值，需要通知Ruyi打包评估】的特征”的未合入PR，感觉可以考虑提前提一下（但是需要按照状态强调下）

> 规则实现：简单正则表达式即可完成初筛；LLM（可选）用来阅读PR长描述，提炼一句话摘要，解决commit message写得很简略的情况。

### Step3：情报汇总输出
每次任务跑完生成一份结构化报告，输出形式可选：
1. Markdown报告（最适合团队阅读）
2. JSON结构化数据（可以直接对接Ruyi后台，作为打包决策输入）
3. 通知推送：飞书/企业微信/邮件告警（**只有高价值更新才推送，普通变更静默存档**）

报告字段示例：
- 仓库名称 | 合并时间 | PR/Commit链接 | 变更简述 | 分类（开发板支持 / ISA扩展 / Bug修复） | 评估建议（是否评估打包新GNU二进制）

### Step4：状态持久化（防止重复告警）
云端存储最后一次扫描的截止时间点（可以放在GitHub Gist / 简单KV存储）。
下次定时任务，**只扫描上一次时间点之后新增的合并PR/commit**，不会重复推送旧情报。

## 三、两种实现方案对比（按需选择）
### 方案A：纯规则匹配（优先推荐，低成本、稳定、无LLM依赖）
- 实现：GitHub Actions + GitHub API + Python 小脚本（几百行代码）
- 能力：关键词+路径正则过滤，自动筛选RISC-V相关提交；生成清单；匹配关键词标记高价值更新
- 优点：稳定可控，成本免费；不依赖第三方大模型；可长期运行；输出结果可复现
- 局限：commit message描述模糊时，识别能力有限；复杂PR需要人工复核

### 方案B：规则+轻量LLM增强（情报质量更高）
在方案A基础上，把初筛出来的高价值PR描述丢给LLM，做：
1. 提炼变更核心目的
2. 判断：这个更新是否会影响GNU工具链二进制输出，是否适合Ruyi打包分发
3. 自动生成简短评估意见
> 适合：commit写得很简略，需要阅读PR长篇描述才能判断场景；LLM仅做摘要和分类，**不做代码编译/测试**

## 四、边界与取舍（贴合Ruyi包管理器场景）
1. **只监控主线合并内容，不监控未合并PR**：上游没合入主线的特性，暂时不纳入打包评估，避免跟踪临时草稿  ——> 这个其实未合入也可以加入（知道谁正在做什么或者推进什么）
2. 不做构建验证：这个系统是**情报收集器**，不是CI构建系统。它只回答：上游有没有发生值得关注的变更；是否需要人工启动构建、测试、打包GNU二进制。最终打包验证仍然由Ruyi SDK流水线完成。
3. 扫描周期：推荐每周一次；如果需要更及时可以缩短；月度适合做定期汇总报告。

## 五、最简落地路线（快速启动）
1. 创建一个独立GitHub仓库，存放监控脚本 + workflow配置文件
2. 配置GitHub Actions cron定时任务（例如每周一凌晨执行）
3. 配置GitHub token，调用API读取binutils-gdb/gcc/glibc镜像仓库的合并PR/commit
4. 编写正则过滤规则，筛选riscv相关变更，标记高价值项
5. 配置输出：自动生成Markdown报告，推送到仓库issue，或者飞书通知
6. 迭代优化关键词库（持续补充：K3、各类RISC-V扩展、profile关键词）

上面这个思路我过了一遍：90%我都觉得认可，可以参考这个思路。
重点：
1. 不需要通过源码去分析。建议只是从commit info、pr info等提交元数据中初步分析。（源码太大，操作难度大，而且我们不是gnu的维护者和测试者，只是获取情报）
2. 我建议方案B：在方案A得到的过滤信息的基础上，结合LLM 自动生成剪短评估意见
3. 与方案意见不同的点：我觉得未合入的pr在某些时候同样有价值。但是鉴于一周一次的更新频率，目前只考虑合入的pr也可以。可以试每周gcc等核心仓库的更新信息数量来调整。信息太多就先不管未合入的pr，如果每周信息不多，则可以把未合入的pr加入进来。但是需要按照状态分开。
