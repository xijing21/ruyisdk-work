Cloudflare的统计功能有两个层级，容易混淆，简单说明一下区别：

- **Web Analytics**：统计单个站点的“真实用户流量”，通过JS代码收集页面浏览量和访问量，会过滤掉爬虫、自动请求等非用户流量，聚焦于用户行为分析。
- **账户分析（Account Analytics）**：汇总账户下**所有站点**的合并数据（总请求量、总带宽、总访问量等），**包含所有流量类型**（包括脚本、自动请求、爬虫等），数据更全面。数值通常比Web Analytics高，适合项目整体汇报时提供“合并总览数据”。

这两个功能的核心差异在于**数据来源和统计口径**。简单来说，**账户分析（Account Analytics）更接近“总览大盘”，而 Web Analytics 更偏向“用户视角”**。


### 📊 Web Analytics 的主要指标

这个工具通过在网站植入的JS脚本来收集数据，核心关注"真实用户"的浏览行为。

*   **Core Web Vitals（核心网页指标）**：衡量用户体验的关键指标，如加载速度、交互响应和视觉稳定性。
    *   **LCP (最大内容绘制)**：页面**主要内容**（如大图、标题）加载完成所需的时间。"良好"标准为 ≤ 2.5秒。
    *   **INP (与下一次绘制的交互)**：页面**整体**对用户点击、敲击键盘等所有操作的响应速度。"良好"标准为 ≤ 200毫秒。
    *   **CLS (累积布局偏移)**：页面内容在加载过程中**意外发生偏移**的程度，是一个无单位得分。"良好"标准为 ≤ 0.1。
*   **Page load time（页面加载时间）**：页面加载所需的总时长。它的总时长并不等于上述子项之和，因为其中还包含一些未单独显示的环节（如预解析）以及各指标间无法归因的空白时间。它包含以下可细分的加载阶段：
    *   **DNS**：DNS 查询耗时。若连接复用或使用缓存，该值可能为 0。
    *   **TCP**：建立 TCP 连接（含 TLS 协商）的耗时。
    *   **Request**：从发出 HTTP 请求到收到首个字节（TTFB）的耗时。
    *   **Response**：从收到首个字节到接收完最后一个字节的耗时，即资源下载时间。
    *   **Processing**：浏览器渲染页面（含加载阻塞资源，如图片、脚本、样式表）的耗时。
    *   **Load Event**：浏览器触发 `load` 事件（文档及资源加载完成）的耗时。
*   **Visits（访问量）**：一次由外部网站或直接链接发起的访问会话。一次访问可以由多个页面浏览构成。
*   **Page views（页面浏览量）**：一次成功的 HTML 页面响应，即用户成功加载了一个页面。
> Cloudflare Web Analytics 的 Core Web Vitals 和页面加载时间数据，均来自**真实用户访问会话（Real User Metrics）**，而非实验室模拟数据，且对 100% 的页面浏览量进行测量，无任何采样。

### 📈 账户分析（Account Analytics）的主要指标

这个工具汇总了账户下**所有站点**经过Cloudflare网络的流量数据，它记录的是所有HTTP请求，数据更原始和全面。

*   **Requests（请求数）**：一个HTTP请求。一次页面访问可能会产生几十甚至上百个请求（如加载图片、脚本、样式表等）。
*   **Bandwidth（带宽）**：从Cloudflare边缘网络发送给客户端的字节总数。
*   **Visits（访问量）**：与Web Analytics的定义类似，指一次由外部网站或直接链接发起的访问会话。一次访问可以由多个页面浏览构成。
*   **Page views（页面浏览量）**：与Web Analytics的定义类似，指成功的HTML响应。

### ✅ 哪个指标最接近“用户数”？

Cloudflare Web Analytics **不直接提供 UV**（独立用户数），而是提供 **Visits（访问人次）**, Visits 能反映网站的活跃度。

一次 **Visit（访问）** 定义为：**一个用户从进入网站到离开（或闲置超时）的完整会话过程**。

举个例子方便理解：

- 用户A打开 `ruyisdk.org`，浏览了3个页面 → 算 **1次 Visit**
- 用户A关闭浏览器，2小时后又回来浏览了2个页面 → 算 **第2次 Visit**（因为间隔太久，会话已过期）
- 用户B在同一时段也打开 `ruyisdk.org`，浏览了1个页面 → 算 **1次 Visit**

所以：
- **Visits ≈ 访问人次**（来了多少次）
- **Page Views ≈ 浏览页数**（看了多少页）

两者关系通常是：**Page Views ≥ Visits**（因为一次访问可能浏览多个页面）。

**与“独立访客（UV）”的区别:**

| 指标 | 含义 | 类比 |
|------|------|------|
| **Visits** | 会话次数（可重复计数） | 进门次数 |
| **Unique Visitors（UV）** | 去重后的独立用户数 | 进门人数 |

如果需要了解“有多少独立用户来过”，目前的技术方案通常依赖Cookie，需用户授权，涉及数据收集和处理，
Cloudflare 技术方案在设计上不使用任何客户端状态（如Cookie或localStorage）来收集指标，也从不精确识别个别用户，它通过分析HTTP请求的来源来统计“访问量”和“页面浏览量”，而不是通过Cookie或IP地址去追踪单个用户的行为。


> 注意：在“账户分析”中，`Visitors`是直接对标“独立IP”的指标。官方文档也明确指出，因为基于IP统计，Cloudflare统计的访问者数量可能会比其他分析工具（如Google Analytics）要高，因为它不会过滤掉那些不执行JavaScript的请求（如爬虫、自动化脚本）。
> 若想了解**真实的用户访问会话规模**，则 Web Analytics 里的 `Visits` 更合适。


### 地域数据将 China 和 HongKong 分开展示的问题，是否可以自定义地域项？

在现有的 Cloudflare 账户分析（Account Analytics）功能中，用户是**无法直接修改或合并**“China”和“Hong Kong”这两个地域展示选项的。

China 和 HongKong 分开展示的问题是 Cloudflare 全球网络在数据展示上的一种通用做法。它通常遵循国际通用的国家/地区代码标准（如 ISO 3166）来区分和展示不同地域的流量数据，因此会将 Hong Kong 作为一个单独的地区列出。

虽然无法直接修改图表，但可以考虑：
1. 在展示“账户分析”数据时，可以添加一个简短的注释。例如，**“根据 Cloudflare 数据统计惯例，香港地区数据在此展示中单列，其实际归属地位于中国。”** 这能将技术工具的展示方式与国家立场明确区分开来。
2. 可以联系 Cloudflare 的账户团队，探讨是否可以通过“自定义区域”功能，将香港和中国大陆定义在一个区域中，使相关数据的处理或统计归属逻辑符合你的要求。

**说明：** 在 Cloudflare Analytics 中，地域（Location）数据是基于访问者的 IP 地址归属地来确定的，而不是用户实际所在的物理位置。当用户通过 VPN、代理服务器或中转节点访问网站时，Cloudflare 识别到的是代理服务器的出口 IP 归属地，而不是用户真实所在的国家或地区。
 RuyiSDK 是开源项目，技术用户群体使用代理访问 GitHub Pages 或国外云服务是常态，当前地域访问数据表现香港和新加坡访问量高于中国是合理的。

**建议：**
> 地域数据基于 IP 归属地统计，访问者使用代理节点访问会导致访问IP与真实物理位置有差异，不代表实际用户物理分布。该数据可用于观察跨境访问趋势，不建议直接作为用户地域分布依据。
