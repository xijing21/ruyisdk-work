# RuyiSDK 产品叙事逻辑总结
## 一、核心叙事逻辑（一句话概括）
> **openRuyi 是在操作系统侧把各家开发板整合成统一系统镜像；RuyiSDK 则是在工具链和开发侧，把零散的 RISC-V 生态“收拢到一起”。**
两者定位互补：RuyiSDK **不做上游统一**（人力不够，也不现实），而是做一层**抽象与托管**——将厂商各自的工具链、固件、镜像收拢进来，**对开发者屏蔽差异**。

---

## 二、三大叙事主线（会议确定的叙事框架）
### 叙事1：一站式开发流程（主线，“开箱即用”是基调，不可动摇）
面向**零基础入门用户**，开局只要求用户知道一件事——**开发板型号**，其余全部由 IDE 引导完成：
```
选平台 → 选开发板型号 → 自动推荐工具链（一键下载）
→ 一键下载固件 → 一键刷入 → 推荐定制化 Demo → 一键运行
```
- 用户拿到板子“什么都不用做”，打开 IDE 即可跑起来，**心智负担最小化**。
- 默认环境不求性能最优，只求“能跑起来”；用户进阶后可在 packages index 中自主检索、切换定制化工具链（第二阶段）。

### 叙事2：多开发板批量化验证（延伸叙事）
- 场景：企业开发者（如腾讯）开发了应用，需要验证其在多块不同厂商开发板上运行结果是否一致。
- 痛点：RISC-V 生态碎片化是公认问题，应用在 A 板能跑、B 板跑不了；开发者不可能为 10 块板装 10 个 IDE。
- 方案：电脑连接多块开发板，IDE 中勾选板子 → **一个按钮批量完成工具链下载、固件刷入、应用用例运行**。
- 前提：以“板子出厂默认系统”为基准做验证，不额外屏蔽 OS 层差异（如做则可与 openRuyi 品牌联动）。

### 叙事3：面向开发板厂商的定制化集成
- **关键定位：面向开发板厂商合作，而非（仅）SoC/平台厂商**——终端用户买到的是开发板，不是 SoC。
- 很多开发板厂商（如 Milk-V、百问网）**没有自己的 IDE**，RuyiSDK 提供通用 IDE 入口，帮厂商触达开发者。
- **精细化定制举例**：迦南（K230）自己的 IDE 不可能内置 CyberCam 专属 Demo（摄像头 + KPU），而 RuyiSDK 可针对“K230 + CyberCam”这一具体板卡组合提供定制化开发环境，开发者无需关心外设差异。
- 开发板厂商常对上游工具链/SDK 做过修改（如 Milk-V Jupiter 对进迭时空工具链的修改），只提供通用工具链的**精细化程度不够**。

## 三、技术底座：资源重组规范
| 层面 | 内容 |
|---|---|
| **问题** | 各厂商 SDK 仓库组织方式五花八门（Buildroot 式大杂烩 / 分散多仓库），公开资源与内部实际用的不一致，固件“放在犄角旮旯” |
| **方案** | RuyiSDK 定义**自己的规范**：无论上游如何组织，统一按“工具链 / 镜像 / 固件 / Demo / GDB”**分类重组登记**到 packages index |
| **落地** | IDE 根据开发板型号检索资源 → 通过 ruyi 下载 → 按规范存放（`toolchain/`、`application/` 等目录）→ 配置文件描述整套编译、调试、运行环境 → 一键构建/运行 |

**关键认识**：如果只做“资源汇总托管”，RuyiSDK 就只是一个资源汇总网站，没有优势。必须**定规范 + 主动与厂商合作建立授权关系**，让厂商提供必要资料（多数整理工作可自己完成，99% 不需厂商额外投入）。

## 四、调试侧叙事
- **调试层级区分**（ clarified in meeting）：
  - **应用层调试**（跑在 Linux 上）：gdb client + 板端 **gdb server**，无需 OpenOCD/JTAG；
  - **底层/裸机调试**：OpenOCD + JTAG，通过 GDB 远程协议转接，gdb client 通用。
- gdb client 与 gdb server 同源编译出的配套程序，厂商魔改 gdb 时（如私有寄存器、私有指令，如进迭时空）通用 gdb 无法显示。
- **对厂商的要求**（仿 openRuyi “支持你，但你要满足条件”模式）：提供**厂商定制版 GDB / gdb server**（只要不魔改得面目全非即可打包进来），gdb 通常随工具链一并托管。
- VS Code 已自带图形化调试方案，RuyiSDK 侧工作量和成本较小。

## 六、叙事亮点提炼（可直接对外讲的卖点）
1. **开箱即用**：开局一块开发板型号，IDE 提供一切——一键部署环境、一键构建、一键运行。
2. **一个 IDE 通吃多家板卡**：解决 RISC-V 生态碎片化，开发者无需安装/选配各厂商工具链。
3. **板卡级精细化定制**：针对具体开发板组合推荐专属工具链、固件与 Demo（如 CyberCam 摄像头 + KPU 场景）。
4. **多板批量化测试**：一台电脑连接 N 块开发板，一键完成环境部署、固件刷入与跨板应用验证。
5. **生态托管而非上游统一**：低成本、可持续——与厂商合作 + 授权，以自有规范重组资源，是 openRuyi 生态中开发侧的一环。
