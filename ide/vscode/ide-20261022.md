## 一、背景与产品定位
RuyiSDK IDE 是一款基于 **VSCodium**（VS Code 开源版本）定制化开发、面向 RISC-V 架构开发的集成开发环境，定位为**面向终端用户的开箱即用产品**，核心目标是为 **RISC-V 架构开发**提供支持。
用户安装可执行程序（Windows exe、Linux 二进制包、macOS 安装包等）后，即已完成 RuyiSDK 全部自研插件的部署，无需再手动检索和安装插件，直接获得完整的 RISC-V 开发体验。

本次会议在产品定位之外，进一步明确了两项关键共识： **自研插件按“是否依赖 ruyi 包管理器”进行拆分，以及 IDE 与插件采取差异化更新节奏。**

---

## 二、技术组织方式
整体技术组织分为两个层面：**IDE 基线层**与**自研插件层**。

### 2.1 IDE 基线
会上讨论了两种组织方式，未最终拍板，倾向于后者：

**方案 A：fork VSCodium 仓库**
- 在 RuyiSDK 组织下 fork VSCodium，维护一个组织下游版本。
- 所有定制直接以 commit 形式落在 fork 仓库中。

**方案 B：基线声明 + 补丁（倾向方案）**
- 不 fork 仓库，而是在 RuyiSDK 仓库中以**声明式配置**定义 IDE 基线，内容至少包括：
  1. **VSCodium 版本基线**：锁定上游具体版本号；
  2. **定制化代码 / 补丁（patch）**：品牌、配置、功能等差异以 patch 形式集中维护；
  3. **打包时预装的插件及版本号**：作为构建配置的一部分；
  4. 其它必要信息（产品名、图标、默认设置等）。

方案 B 的优势在于：上游同步成本低、定制差异清晰可审计、便于 CI 按配置精确复现构建。**该选择需在后续技术评审中正式确认。**

### 2.2 RuyiSDK 自研插件

自研插件由 RuyiSDK 组织独立维护，随 IDE 发行包预装，已知包括：

| 类别 | 说明 | 命名状态 |
|---|---|---|
| ruyi 包管理器客户端插件 | ruyi CLI 的图形化前端 | 已定：`ruyisdk` |
| RISC-V 开发辅助插件 | 代码高亮、调试支持等 RISC-V 开发能力 | **待定**（暂称 riscvXXX） |
| 其它扩展插件 | 面向未来的可扩展能力 | 按需增加 |

## 三、产品定义
1. **交付形态**：RuyiSDK IDE 可执行程序（exe、Linux 二进制包等），开箱即用，预装全部自研插件。
2. **构建方式**：通过 **CI 自动化打包**，杜绝人工打包导致的不一致与易错问题。
3. **打包节奏**：打包时机与频率由人工维护，**当前建议一年发布一个版本**。

---

## 四、版本策略

产品采用**双轨版本号体系**，两套版本各自服务不同目的：

| 版本体系 | 格式 | 用途 | 示例 |
|---|---|---|---|
| 对外宣传版本 | 年份式（CalVer） | 用户与市场沟通 | 比如 RuyiSDK IDE 2026 （仅示意，待定） |
| 对内研发版本 | 语义版本 X.Y.Z（SemVer） | 仓库、CI、构建工件、插件版本维护 | 比如 1.0.0 （仅示意）|

自研插件同样遵循语义版本规范，独立发版，版本节奏与 RuyiSDK 整体迭代节奏保持一致。
> **注**：对外版本是否采用"2026"这类年份式编号、与内部 SemVer 的映射关系，建议在版本规范文档中固化，避免歧义。

## 五、CI 构建配置要求

CI 构建需要一套**明确的配置说明**作为唯一构建输入，会上初步列出的字段包括：
- 产品名称：RuyiSDK IDE
- 产品版本号：2026（对外）
- 构建时包含的插件清单及各自的版本号
- 其它必要信息（待 CI 方案设计时补充细化，如 VSCodium 基线版本、目标平台与架构、补丁清单等）
该配置文件应做到：**人工维护一份配置 → CI 即可产出一致、可复现的发行包**。

## 六、版本更新与兼容性
1. **发布节奏**：RuyiSDK IDE 计划一年发布一个版本。
2. **插件使用原则**：用户安装后，**默认建议使用 IDE 发行包内置的插件版本**，以保证整体兼容与体验一致性。
3. **独立更新**：允许用户对插件进行独立更新，但**必须参考插件的版本依赖与兼容性说明**，该说明文档是必备交付物。
4. **产品组职责**：需制定并维护**更新策略与兼容性维护规划**，明确插件与 IDE 基线之间、插件相互之间的兼容关系声明方式。
